# Spec: auto-evolve-post-continuation-scout-window

## Goal

Resolve the current pending Harness evolution window by evaluating whether the
five candidate archives contain reusable process lessons that should be
promoted into durable Harness rules/templates/lint, retained in current docs,
merged with existing rules, retired, or left archive-only.

## Users

- Future AHO coding agents that rely on `AGENTS.md`, `docs/ECL.md`,
  `docs/STATUS.md`, and review templates for current operating rules.
- The project owner, who needs Harness evolution to reduce repeated mistakes
  without turning archive history into a growing documentation burden.

## Acceptance Criteria

- AC-001: The pending archive window is evaluated in a written proposal under
  `harness/evolution/proposals/` with accepted/rejected candidates and an
  Experience Retention Scan.
- AC-002: Independent subagent review is recorded with scope, recommendation,
  score, rationale, and limitations.
- AC-003: If a durable Harness delta is accepted, it is narrowly applied to the
  right Harness owner and verified; if no delta is warranted, the no-op
  rationale explains why existing rules are sufficient.
- AC-004: `harness/evolution/results.tsv` receives one terminal row and
  `scripts/harness-evolve.ps1 mark-complete` clears the pending state.
- AC-005: Handoff docs and active change closeout accurately state no active
  product change, no pending evolution after completion, latest archive path,
  and next recommended product direction.

## Non-Goals

- Product runtime, Workbench UI, Scheduler, Goal Loop, validation, audit, apply,
  close, merge, or remote behavior changes.
- New evidence families or additional explanation layers.
- Promoting archive-specific sandbox paths, run ids, timing chronologies, or
  one-off bug details into current handoff docs.
- Full-auto task mode, parallel executor, Scheduler loop, whole-wave dispatch,
  child Change auto creation, or automatic apply/merge/close.

## Constraints

- `harness/evolution/pending.md` is a maintenance reminder, but once this
  evolution has started it must finish with proposal, review, validation,
  results row, and `mark-complete`, or be parked/blocked.
- Subagent review is allowed by the user but remains read-only and does not
  replace ECL lifecycle or own canonical edits.
- `harness/changes/INDEX.json` must be regenerated by script, not hand edited.
- `README.md` remains unrelated and untracked.

## Risks

- Over-promoting product-specific lessons into generic Harness rules would
  increase context cost and slow future product work.
- Under-promoting repeated real acceptance or verification lessons could allow
  the same mistakes to recur.
- Handoff docs can drift if close updates do not remove active/pending state.
